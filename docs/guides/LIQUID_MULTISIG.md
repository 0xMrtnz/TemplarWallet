# Liquid multisig

A multisig wallet can now span both chains: an M-of-N Bitcoin wallet and an
M-of-N Liquid wallet, created together, listed as **one** wallet entry. This
document is the design, the limits, and the test plan.

## What gets built

| | Bitcoin | Liquid |
|---|---|---|
| Descriptor | `wsh(sortedmulti(M, …))` | `ct(slip77(K),elwsh(multi(M, …)))` |
| Co-signer key | `[fp/48'/1'/0'/2']tpub…` (BIP48, P2WSH) | `[fp/87'/1'/0']tpub…` (BIP87) |
| Key order | sorted per BIP67 | **as given** — `multi`, not `sortedmulti` |
| Where it lives | `WalletProfile::Multisig` | `entry.liquid` (`LiquidWalletConfig`) |
| Engine | BDK 0.30 | LWK 0.9 (`Wollet`, watch-only + explicit signing) |

One registry entry, two chains — the same shape a hardware wallet already uses
(`has_bitcoin()` / `has_liquid()` decide which UI surfaces exist).

### Why two keys per co-signer

Liquid derives from its own account. `m/48'/1'/0'/2'` and `m/87'/1'/0'` are
different branches of the same seed, and no public key can be walked sideways
into another branch — so both are collected at setup. This is free for every
key whose seed the app can reach (generated in-flow, typed in, or another app
wallet) and for a Jade (one extra call in the same unlocked session). Only a
co-signer who pastes an xpub from elsewhere has to send two.

Reusing the BIP48 key on both chains was considered and rejected: it would put
identical public keys in both chains' scripts, so anyone watching both could
link the two wallets permanently.

### The blinding key

Random SLIP77, generated by the coordinator, embedded in the descriptor every
co-signer imports. Not ELIP151 — a Jade's multisig registration carries 32 raw
SLIP77 bytes and has nowhere to put a descriptor-derived key.

Note this inverts the *singlesig* Jade rule ([`liquid/hardware.rs`](../crates/templar-core/src/liquid/hardware.rs)
module docs): there the descriptor must carry the key read *from* the device;
here the device is told which key to use, as part of registration.

## Limits

1. **Only a Jade can sign Liquid on hardware.** Ledger, Trezor, Coldcard and
   KeepKey are Bitcoin-only in firmware — an Elements sighash commits to
   33-byte value and asset commitments where BIP143 commits to an 8-byte
   amount. A key read from one of those devices turns Liquid off for the whole
   wallet, stated in the wizard before anything is created.
2. **Enough keys must be able to sign.** The backend refuses a Liquid side
   whose threshold exceeds the number of Liquid-capable keys — otherwise funds
   arrive at a wallet that can never spend them. A *pasted* key is unknowable
   (its owner may hold a Jade or a software wallet), so it counts as capable
   and the review step says so.
3. **No QR transport.** A PSET has no BC-UR encoding here, and Jade's QR mode
   is Bitcoin-only. Co-signing travels as base64 text or a `.pset` file.
   Air-gap multisig therefore stays Bitcoin-only.
4. **No Miniscript on Liquid.** Policy wallets (timelocks, hashlocks, thresholds)
   have no confidential-descriptor form here, so the coins question offers
   Liquid for single-key and multisig only.
5. **New wallets only.** An existing Bitcoin-only multisig cannot gain a Liquid
   side: its BIP87 keys were never collected, and its local seeds were never
   stored. Recreate it with the same co-signer keys — same Bitcoin addresses,
   same funds, plus a Liquid side.
6. **Testnet only**, like the rest of the app.

## Signing model

The Bitcoin side embeds each local xprv in the descriptor, so BDK signs with
every local key in one pass. LWK cannot work that way: `SwSigner` matches on the
**master** fingerprint and derives the whole origin path itself, so an
account-level xprv is useless to it. The Liquid side therefore stores the local
seeds on the profile (`WalletProfile::Multisig::local_mnemonics`), sealed at
rest by the vault exactly like `Software { mnemonic }`, and signs from those.

A send from a multisig signs with every local seed, then:

- threshold met → finalize and broadcast, returns the txid;
- short → returns `{partial_pset, sigs_have, sigs_needed, chain: "liquid"}`,
  which the send screen turns into the co-signing dialog. Nothing is broadcast.

Co-signers load that PSET under **Send › Co-sign**. The screen detects the
chain from the payload's magic bytes (`pset\xff` vs `psbt\xff`), so the same box
takes either. Signing in turn (A → B → C) keeps it to one file; parallel copies
can be merged with `combine_psets` (backend op, no UI yet).

### Threshold counting

LWK's `fingerprints_missing()` lists every key without a signature, so on a
2-of-3 it is never empty — its `is_complete` cannot be used as a quorum test.
`PsetDetails::sigs_present_min` counts signatures on the *least*-signed input,
which is the number that must reach M.

## FFI surface

| Method | Purpose |
|---|---|
| `create_multisig_wallet` | now takes `liquid_xpubs[]` + `liquid_capable_keys` |
| `derive_liquid_cosigner_xpub` | BIP87 key from a mnemonic |
| `get_liquid_cosigner_xpub` | BIP87 key of an app wallet |
| `get_jade_liquid_cosigner_xpub` | BIP87 key from a connected Jade |
| `inspect_pset` | fee, recipients, signature count (needs the wallet open) |
| `sign_pset` | sign with local seed(s) |
| `sign_pset_hw` | register the multisig on a Jade, then sign |
| `combine_psets` | merge parallel-signed copies |
| `broadcast_pset` | finalize + broadcast |

## Test plan

### L1 · Create (software keys, no hardware needed)
Wizard → software → **Multisig** → coins step now offers **Bitcoin + Liquid**
→ 2-of-2 → generate the creator key → back up → verify → second key: **New key**
→ review.

- **Expect:** review says *Bitcoin + Liquid*, and the created wallet's card in
  the picker shows both chains.
- Wallet Info shows a `ct(slip77(...),elwsh(multi(2,...)))` descriptor — check
  it contains `slip77(`, never `elip151`.
- Negative: set the second key to **USB device** with a Ledger attached → the
  slot says the device is Bitcoin-only and the review switches to *Bitcoin
  only* before anything is created.

### L2 · Receive and sync
Open the wallet → Receive → Liquid → address starts `tlq1…`/`vjT…`. Fund it
from the faucet, sync, confirm the balance.

### L3 · Send needing a co-signature
Send some L-BTC. The wallet holds one of the two keys, so the send returns the
co-signing dialog: *1 of 2 signatures collected*, nothing broadcast.

- Copy the PSET, or save the `.pset` file.
- Load it back under **Send › Co-sign** on the co-signer's app → it is detected
  as Liquid → recipients and fee are readable → **Sign** → the count rises.
- Return the signed PSET to the first wallet's dialog → **Review & Broadcast**.
- Negative: paste a copy that is still short → refused with how many
  signatures are missing, no broadcast attempt.

### L4 · Jade as a co-signer (needs the device)
Enroll a Jade in the multisig: its Bitcoin key comes over USB as before, and
its BIP87 Liquid key is read in the same step.

- **Expect:** the slot shows *Liquid key ready* with an `[fp/87'/1'/0']tpub…`.
- Co-sign a PSET with it: **Sign with device** in the co-sign view →
  the wallet is registered on the Jade (16-char name, confirm on screen, once
  per device) → then the signature request appears.
- Negative: decline the registration → tagged `DEVICE_NOT_READY` with the
  device's own reason, not a signing error.

Untested on real hardware at time of writing — same caveat as the rest of the
native Jade work (see [`HARDWARE_TESTING.md`](HARDWARE_TESTING.md) §5b).
